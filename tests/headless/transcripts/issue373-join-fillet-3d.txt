# issue #373 — JOIN of two non-coplanar-looking 3D polylines dropped a vertical/near-vertical run,
# and FILLET could not touch two lines whose endpoints are not both at world Z=0.
#
# JOIN's edge walk only ever compared X/Y at each endpoint and always wrote 0 for the joined
# polyline's own Z, so two 3D polylines sharing a plan location at different elevations fused onto
# the wrong endpoint and every vertex landed on Z=0. FILLET's two-line solve was pure 2D throughout
# (FilletCurve, SolveFilletCenter, the arc it built) so a picked line's own Z was silently ignored.
#
# LINE's own typed input has no X,Y,Z form (3DPOLY does; a plain LINE silently drops a third field —
# a separate, pre-existing, documented limitation, not part of this fix). ELEV changed BETWEEN two
# picks of the same LINE is what builds a true 3D line segment here instead.

# ── 1. JOIN of two 3D polylines preserves every vertex's Z ─────────────────────────────────────
NEW
CMD 3DPOLY
CMD 0,0,0
CMD 0,0,10
CMD END
CMD 3DPOLY
CMD 0,0,10
CMD 10,0,10
CMD END

CHECK ALL
EXPECT POLYLINES 2

CMD JOIN
CLICK -5 -5
CLICK 15 5
EXPECT SELECTED 2
CMD
EXPECT LOG JOIN — created 1 polyline(s).
CHECK ALL
EXPECT POLYLINES 1
# All three vertices survive with their own Z — nothing collapses to 0.
EXPECT POLYVERT 0 0 0 0 0
EXPECT POLYVERT 0 1 0 0 10
EXPECT POLYVERT 0 2 10 0 10

# ── 3. FILLET of two parallel 3D lines connects them with a semicircle, in 3D ───────────────────
# Line 2 is drawn flat, then MOVEd up by Z=5 as a rigid whole (a plain LINE's own typed input has no
# X,Y,Z form — only 3DPOLY does) — two lines this way are still exactly coplanar (any two parallel
# lines are), so this exercises the plane build, the projected 2D solve and the 3D semicircle special
# case end to end, with hand-computable expected numbers.

# the tangent point, so neither line's stored endpoints change.
EXPECT LINEXYZ 0 0 0 0 10 0 0
EXPECT LINEXYZ 1 0 3 5 10 3 5
EXPECT ARCPOINTS 0 0 0 0 0 3 5

# ── 5. FILLET's own pick now accepts the camera ray (plumbing smoke test) ───────────────────────

# object at pick", because FILLET's click handler never received the camera ray PickClosestCadEntity
# already knows how to use — it only ever got the click's flattened work-plane X/Y. FILLET now takes
# an optional ray and CLICK's own Z form aims one, the same way CadResolveSolidPick's ray already
# does. This checks the new parameter is actually wired end to end (CadUi.cpp -> SubmitViewportPick
# -> SubmitViewportPickImpl -> HandleFilletViewportPick -> PickClosestCadEntity) and does not
# regress an ordinary flat pick once the view is orbited. It cannot reproduce the exact screen-ray

# ── 8. The camera-ray pick fixes a real report: small-radius fillet rounding the WRONG side ─────
# A pick projected exactly onto its own line cannot tell two valid tangent arcs apart — it is
# equidistant from both candidates, so the "nearest to pick" tie-break falls back to iteration
# order, and could round the OUTSIDE of the corner instead of the inside. A right-angle corner
# (vertical then horizontal, same shape as the report's screenshot) with an orbited view and a CLICK
# Z that lands slightly OFF each line, toward the interior of the corner, is what a real screen
# click naturally provides — this is what the ray-plane intersection now recovers.
NEW
CMD 3DPOLY
CMD 0,0,0
CMD 0,0,10
CMD END
CMD 3DPOLY
CMD 0,0,10
CMD 10,0,10
CMD END
VIEWANGLES -45 35
CHECK ALL
EXPECT POLYLINES 2

EXPECT LOG FILLET — 3D corner filleted.
