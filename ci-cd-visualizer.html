From pull request to shipped installer

Four independent GitHub Actions workflows handle PR checks, release packaging, the marketing site, and CodeQL. Product releases are deliberately manual; the selected branch determines whether the run creates a stable release, updates the rolling beta, or leaves a downloadable artifact. This map reflects the current remote beta configuration and recent runs, which are ahead of this checkout’s branch.

A manual run still builds and packages. It uploads installer + manifest as a workflow artifact.

No GitHub Release or tag
Build and package steps, in order
  • Checkout; prepare MSVC and Ninja; start sccache.
  • Resolve version/channel. On master, check whether remote tag already exists.
  • Configure CMake with GOSURVEY_ENABLE_ANALYZE=ON, but GOSURVEY_BUILD_HEADLESS=OFF and GOSURVEY_BUILD_TESTS=OFF; build GoSurvey.exe and bundle resources.
  • Assert required What's New assets exist; upload GoSurvey.exe, pdfium.dll, and resources as gosurvey-bin.
  • Dependent package job downloads them, obtains the VC++ redistributable, builds Inno Setup installer, then writes update manifest (version, URL, SHA-256, size, format compatibility, notes).
  • Signing step is currently a no-op: installers are unsigned. Then branch-specific upload/publish occurs.

Other automation

These do not form a release prerequisite.

🌐 Pages deployment

Ubuntu runner → checkout → configure Pages → copy What's New PNGs into site/img/features → upload site artifact → deploy to GitHub Pages. New product releases do not trigger a site deployment; site reads release data from GitHub API at view time.

🛡️ CodeQL C++ analysis

Daily matrix → check out master and beta in parallel → initialize C++ security-and-quality queries → configure/build with MSVC + Ninja → upload analysis. Error-severity findings fail the scan; pull requests do not trigger CodeQL.

What the configuration says about confidence

These are direct workflow and branch-protection observations; timing rows link to hosted runs.

High impactRelease dispatch does not repeat PR tests

The full build, CTest, clang-tidy and MSVC analysis are required before changes merge to master or beta. The manual release workflow builds and packages from its selected ref without rerunning that test suite.

Evidence: origin/beta pr-checks.yml; release.yml build flags and workflow_dispatch trigger

Security postureUnsigned installers

The signing step only prints a message. SHA-256 in the manifest checks that bytes match, but does not establish who published them; users may see SmartScreen warnings.

Evidence: release.yml “Sign the installer” step

Scheduled coverageCodeQL scans master and beta daily

Both maintained branches receive a daily whole-program C++ security-and-quality scan. Manual dispatch remains available; PRs are not scanned automatically.

Evidence: codeql.yml daily schedule and branch matrix

Build policyWindows jobs repeat some compile work

Full validation configures independent Windows jobs for build/test, clang-tidy and MSVC analysis. The latest pre-optimization build and analysis each spent over 17 minutes compiling. MSVC analysis now builds only diff-affected object targets for ordinary source changes. That run reported zero sccache requests; the MSVC job now verifies launcher injection and reports cache stats, while CMP0141 is set early enough to enable /Z7.

Evidence: run #39599214462; prior sccache stats showed 0 requests; new run will verify reuse

Important boundaryBranch protection is outside these files

The live branch protections for master and beta require PR gate, Gitleaks, Trivy, full build and CTest, clang-tidy, and MSVC analysis; each still requires one approving review.

Evidence: GitHub branch protection API checked for master and beta

User-facing contentRelease notes can fall back silently

If RELEASE_NOTES.md lacks a matching version section, manifest and release body use a generic fallback. The pipeline warns, but does not stop publishing.

Evidence: release.yml “Write the update manifest” step

Coverage audit: no test was removed. The Catch2 cases map to distinct requirements or regressions, headless transcripts assert command-level behavior, and Qt tests cover UI and persistence flows. This repository has no line/branch or mutation coverage report to justify deleting overlapping-looking tests. The 2,726 → 188 change is CTest process batching and sharding, not fewer checks.

The full local CTest run took 107.94s at 8 workers (all 188 registrations passed). The previous hosted CTest took 10m 31s before this sharding and concurrency change; the next Actions run will measure the blocking suite.
